CHOIX TECHNOLOGIQUES — ÉDITEUR DE DOCUMENTS COLLABORATIF AWS
Version : 1.0
Date : 24 octobre 2026

1. OBJECTIF

Construire une application web collaborative hébergée sur AWS, tout en démontrant une démarche d’ingénierie cloud : infrastructure reproductible, automatisation CI/CD, tests de concurrence et de charge, observabilité, sécurité et maîtrise des coûts.

Le projet doit respecter les contraintes fonctionnelles du sujet avant d’ajouter des améliorations. La simplicité, la cohérence et la capacité à justifier les décisions priment sur le nombre d’outils.

2. STACK PRINCIPALE

Frontend et application web
- Next.js avec TypeScript.
- React pour l’interface.
- Les Route Handlers de Next.js servent d’API HTTP pour les opérations classiques.
- Interface d’édition basée sur Tiptap et Yjs.

Collaboration temps réel
- Hocuspocus, service Node.js basé sur Yjs.
- WebSockets pour la synchronisation des modifications et la présence des collaborateurs.
- Le service de collaboration doit disposer d’une stratégie explicite de persistance durable des documents et de récupération après reconnexion.
- Les contrôles de droits, de quota et de validation ne doivent pas être délégués au seul client.

Données et fichiers
- Amazon DynamoDB : métadonnées des documents, quotas, réservations de téléchargement, états des tâches et données nécessaires aux opérations atomiques.
- Amazon S3 : stockage des PDF générés et des fichiers nécessaires à la persistance, selon la conception retenue.
- Les PDF sont immuables par version : une génération correspond à un instantané cohérent du document. Une modification ultérieure ne doit pas changer le fichier déjà généré pour cette version.

Traitements asynchrones
- Amazon SQS : file de tâches pour les traitements différés, notamment la génération ou la préparation des PDF.
- AWS Lambda avec Node.js/TypeScript : exécution des tâches de génération PDF et des traitements asynchrones adaptés.
- Amazon SES : envoi de l’e-mail au créateur lorsque la dernière copie autorisée est réservée.
- Une stratégie de reprise et une dead-letter queue (DLQ) seront prévues pour les messages qui échouent de manière répétée.

3. INFRASTRUCTURE AS CODE

- Terraform pour décrire et provisionner les ressources AWS.
- L’infrastructure doit être reproductible et documentée.
- Les permissions IAM suivent le principe du moindre privilège.
- L’état Terraform doit être géré de façon sûre : backend distant adapté, contrôle d’accès et mécanisme de verrouillage compatibles avec la version utilisée.
- Les ressources, régions, limites et hypothèses de coûts seront décrites dans la documentation.
- Les secrets et clés d’accès ne doivent jamais être codés en dur ni commis dans le dépôt.

4. CI/CD ET QUALITÉ

- GitHub Actions pour les workflows d’intégration et de déploiement continus.
- Sur les Pull Requests, exécuter selon les composants modifiés :
  * formatage et lint ;
  * tests unitaires ;
  * tests d’intégration pertinents ;
  * vérification et validation de la configuration Terraform ;
  * contrôles de sécurité des dépendances et de l’infrastructure.
- Le déploiement doit être contrôlé et suivi d’une vérification de santé.
- Prévoir une procédure de retour à une version précédente lorsque cela est applicable.
- Privilégier une fédération OIDC entre GitHub Actions et AWS plutôt que des clés AWS permanentes stockées dans le dépôt.
- Les opérations destructrices sur l’infrastructure doivent être protégées et documentées.

5. TESTS ET VALIDATION

- Vitest pour les tests unitaires TypeScript.
- Tests d’intégration pour les interactions entre l’API, DynamoDB, S3 et les traitements asynchrones.
- Outil de test de charge à choisir selon le temps disponible, par exemple k6.
- Tester explicitement les scénarios critiques :
  * modifications concurrentes et convergence des éditeurs ;
  * dernière copie disponible demandée simultanément par plusieurs visiteurs ;
  * document modifié pendant la préparation du PDF ;
  * quota quotidien consommé simultanément depuis plusieurs appareils ;
  * répétition d’une même requête et reprise après échec.
- Mesurer latence, débit, taux d’erreur, profondeur de file et résultats des opérations atomiques.
- Distinguer les résultats réellement mesurés des extrapolations. Ne pas prétendre avoir testé un volume qui n’a pas été exécuté.

6. OBSERVABILITÉ

- Amazon CloudWatch pour les journaux, métriques, tableaux de bord et alertes.
- Suivre au minimum :
  * nombre de requêtes et taux d’erreur ;
  * latences des opérations importantes ;
  * réservations acceptées et refusées ;
  * profondeur et ancienneté des messages SQS ;
  * succès, échecs et durée des générations PDF ;
  * erreurs de persistance et de collaboration ;
  * consommation et coûts AWS lorsque les données disponibles le permettent.
- Définir quelques seuils d’alerte pertinents plutôt que multiplier les métriques inutiles.

7. SÉCURITÉ

- IAM avec permissions minimales pour chaque composant.
- Pas de secrets ni de clés AWS dans le code source.
- Validation côté serveur des opérations sensibles.
- Idempotence pour éviter de traiter ou de facturer plusieurs fois une même requête logique.
- Vérification de la configuration de sécurité dans la CI, par exemple avec Checkov ou Trivy, selon la compatibilité retenue.
- Examiner les dépendances et les autorisations avant déploiement.
- Les liens de téléchargement doivent respecter strictement le nombre de copies autorisées. Une URL S3 réutilisable ne doit pas permettre de contourner cette limite.

8. PRINCIPES DE COHÉRENCE ET DE FIABILITÉ

- Réservation d’une copie avant de transmettre la demande au module PDF.
- Mise à jour atomique des compteurs de téléchargement et des quotas, avec les mécanismes conditionnels ou transactionnels adaptés dans DynamoDB.
- Définition claire de la sémantique d’une réservation : la réservation acceptée consomme une copie même si le visiteur interrompt ensuite le téléchargement, sauf décision différente explicitement documentée.
- L’idempotence protège les répétitions d’une même demande logique, mais ne permet pas d’identifier une personne unique si les visiteurs restent anonymes.
- Prévoir le cas où la réservation est enregistrée mais où l’envoi du message SQS échoue : enregistrement durable de la tâche et mécanisme de reprise/réconciliation.
- Une DLQ aide à isoler les échecs répétés, mais ne remplace pas la surveillance et une procédure de traitement.
- La notification du dernier téléchargement doit être durable, unique et réessayable.
- Le service de collaboration doit persister les mises à jour Yjs de façon adaptée ; une simple conversion répétée en JSON ne doit pas compromettre la convergence ni l’historique.

9. COÛTS ET DÉPLOIEMENT

- Une seule région AWS, conformément au sujet.
- Favoriser les services managés pour limiter la charge d’exploitation.
- Estimer les coûts avant les tests de charge et surveiller les dépenses.
- Prévoir une procédure documentée de destruction des ressources après évaluation.
- Vérifier les quotas AWS et la capacité des services avant tout test important.
- Ne pas lancer de tests de charge élevés sans vérifier les coûts, les limites et les effets sur les ressources.

10. CHOIX EXPLICITE : PAS DE KUBERNETES DANS LA VERSION CIBLE

Kubernetes est retiré du périmètre principal. Il ajouterait de la complexité opérationnelle et des coûts sans être nécessaire pour démontrer les objectifs centraux du sujet. L’application utilisera les services AWS managés et un service Node.js distinct pour les WebSockets si l’architecture le requiert.

Kubernetes pourra éventuellement faire l’objet d’une expérimentation séparée, mais il ne fait pas partie des critères de réussite de la version principale.

11. ORDRE DE PRIORITÉ

Priorité 1 — Fonctionnalités et contraintes critiques :
- édition collaborative fiable ;
- quotas et réservations atomiques ;
- PDF cohérents et liens contrôlés ;
- notifications et gestion des échecs ;
- tests des scénarios critiques.

Priorité 2 — Industrialisation :
- Terraform ;
- CI/CD GitHub Actions ;
- contrôles de sécurité ;
- observabilité CloudWatch ;
- estimation des coûts et procédure de nettoyage.

Priorité 3 — Améliorations si le temps le permet :
- tests de charge plus poussés ;
- alertes et tableaux de bord plus complets ;
- stratégies avancées de déploiement et de reprise.

12. POINTS À CONFIRMER AVANT L’IMPLÉMENTATION

- Choix précis de la stratégie de persistance Yjs et de l’historique des révisions.
- Règles de calcul des 10 000 caractères quotidiens : fuseau horaire, Unicode, collage de texte et opérations acceptées.
- Modèle d’identité minimal pour les auteurs et limites de l’anonymat des visiteurs.
- Façon exacte de servir les PDF sans permettre de dépasser la limite de téléchargements.
- Mécanisme de reprise entre réservation DynamoDB et publication SQS.
- Choix de l’outil de charge et taille des tests compatible avec le budget.
- Versions des outils, limites de service et estimation de coûts à vérifier au moment de l’implémentation.
